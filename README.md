# ROUTE

시간, 교통비, 체력을 관리하며 목적지까지 이동하는 웹 경로 퍼즐 게임입니다. 도보·버스·지하철을 조합하고, 플레이한 경로를 서버가 계산한 기준 경로와 비교할 수 있습니다.

## 실행

Node.js 18 이상과 npm이 필요합니다.

```bash
npm ci
npm start
```

브라우저에서 [localhost:3000](http://localhost:3000)을 엽니다. `PORT` 환경 변수로 포트를 변경할 수 있으며, 별도 API 키나 데이터베이스 설정은 필요하지 않습니다.

```bash
npm test
```

테스트는 DOM 환경과 실제 Express 핸들러를 연결해 화면 흐름, 이동, 재도전, 캠페인 연동을 확인합니다. 실제 브라우저의 화면 배치와 터치 조작은 별도로 확인해야 합니다.

## 실제 지도 모드

저장소에 포함된 지하철·버스·도보 공개 자료로 실제 지도 모드를 준비할 수 있습니다. 프로젝트 루트의 Git Bash에서 실행합니다.

```sh
npm ci
node tools/buildCommuteCatalog.cjs
npm run data:check && ROUTE_GRAPH_MODE=subway npm start
```

카탈로그 생성기는 공개 철도 자료와 [서울시 버스 구간 자료](source/seoulWeekdayBus.json)를 방향별 이동 데이터로 합칩니다. 사용 가능한 별도 관측 파일이 있다면 생성 전에 `data/verifiedSegments.json`에 두면 됩니다. [보행 자료](source/seoulPedestrianRoutes.json)는 OpenStreetMap 보행 네트워크에서 역 사이 경로를 계산한 결과입니다. 신규 구간은 보행망 경로 거리와 초당 1.25m를 기준으로 시간을 추정합니다. 기존 광운대역 주변 표본은 [OSRM 보행 경로](https://routing.openstreetmap.de/about.html)의 추정치를 유지합니다. 원천 데이터와 파생 보행 자료에는 [© OpenStreetMap contributors, ODbL](https://www.openstreetmap.org/copyright)이 적용됩니다.

카탈로그에는 양방향 도보 경로가 확보된 간선만 포함합니다. 철도 연결과 석계역·광운대역 연결을 우선 유지합니다. 그 외에는 역마다 도보가 짧은 두 연결과 버스가 가장 빠른 연결을 골라 합칩니다. 다른 역에서 고른 연결도 같은 간선으로 합쳐집니다. 도보 선택 가능 여부는 라운드의 남은 시간과 체력으로 판정합니다.
배포 서버에서는 완성된 `data/commuteSegments.json`을 설치하거나 `ROUTE_SEGMENTS_FILE`에 읽기 전용 카탈로그의 절대경로를 지정할 수 있습니다.

버스는 [서울시 정류장 간 평균 운행시간](https://data.seoul.go.kr/dataList/OA-21217/A/1/datasetView.do)의 2026년 11월 9~13일 08시대 값을 사용합니다. [정류장 좌표](https://data.seoul.go.kr/dataList/OA-15067/S/1/datasetView.do)를 이용해 각 정류장을 약 250m 이내의 가장 가까운 게임 역에 연결합니다. 약 3km 이내 역 쌍에서 정류장 순서가 연속된 직행 기록을 사용합니다. 세 날짜 이상 기록이 있는 노선 중 관측일이 많은 후보를 우선하고, 관측일 수가 같으면 평균 탑승시간이 짧은 후보를 고릅니다. 노선 ID와 유형은 [노선 ID 파일](https://data.seoul.go.kr/dataList/OA-15262/A/1/datasetView.do)과 [노선 기본정보](https://data.seoul.go.kr/dataList/OA-15066/F/1/datasetView.do)를 대조합니다.

정류장 간 원본 수치는 인접 정류장 값의 규모를 근거로 초 단위로 해석했습니다. 승차 전 도보와 하차 후 도보는 각각 게임용 3분입니다. 승차 대기와 실제 지연 여부는 기록에 포함되지 않습니다. 지하철은 표준 운행시간을 사용하며, 레벨별 이벤트 보정은 플레이 중 적용합니다.

공개 자료만 사용한 별도 배포 파일은 `node tools/buildCommuteCatalog.cjs --public-only`로 생성합니다. 결과 파일은 `data/commuteSegments.public.json`이며 `ROUTE_SEGMENTS_FILE`에 지정하면 됩니다. 팀원은 이 생성 파일 대신 Git에 포함된 원본 데이터와 위 기본 실행 절차를 받아 같은 내용을 생성할 수 있습니다.

## 주요 기능

- 15개 레벨, 상황별 캠페인 3종, 일주일 등교, 라운드형 무한 모드.
- 시간·교통비·체력 제약과 환승 요금 규칙.
- 교통 지연·운행 중단 사건, 선택 경유 미션과 결과 이야기.
- 도착·추가 목표·자원 절약을 평가하는 레벨별 별점.
- 같은 지도 재도전, 내 경로와 기준 경로 비교, 경로 재생.
- 모바일 화면, 키보드 선택, 다크 모드, 애니메이션 줄이기.

인접 역을 선택하고 수단 카드를 누르면 바로 이동합니다. 수단 단축키는 `1`·`2`·`3`이며, 이동은 되돌릴 수 없습니다. 생각하는 동안에는 게임 시간이 줄어들지 않습니다.

## 기술 구성

| 구분 | 사용 기술 |
| --- | --- |
| 화면 | HTML, CSS, Vanilla JavaScript, SVG |
| 서버·통신 | Node.js, Express 5, Fetch API, JSON REST API |
| 경로 탐색 | 최소 힙을 이용한 다익스트라 기반 상태 확장 탐색 |
| 저장 | 브라우저 localStorage·sessionStorage, 서버 메모리, JSON 파일 |
| 테스트 | LinkeDOM, Node.js assert |

별도 프런트엔드 빌드 과정은 없습니다.

## 파일 구조

```text
server.js              # API, 세션 관리, 이동·결과 판정
lib/engine.js          # 지도 생성, 이동 규칙, 경로 탐색
routes.json            # 교통수단, 레벨, 캠페인 설정
public/                # 화면 HTML, CSS, 클라이언트 JavaScript
tests/                 # 화면·API 연동 테스트
docs/                  # 발표자 가이드, 기술·데이터 구조 설명
package.json           # 실행 명령과 의존성 정의
package-lock.json      # 설치 의존성 버전 고정
data/                  # 실행 중 생성되는 결과 기록 (Git 제외)
```

## 데이터와 진행 저장

기본 실행은 기존 게임용 지도를 사용합니다. 실제 철도망 미리보기는 게임용 시간을, 저장 모드는 검증한 방향별 이동 기록을 사용합니다.

설정·레벨별 최고 별점은 브라우저에 저장합니다. 진행 중 라운드와 일주일 캠페인은 서버 메모리에 있으며 서버 재시작 시 사라집니다. 현재 화면의 이어 하기는 같은 탭에서만 지원하며 새로고침 후 진행 중 판을 복원하지 않습니다. 서버 결과 기록은 `data/game_history.json`에 최근 최대 500건을 보관합니다.

## 추가 구현 계획

현재 MVP는 게임 규칙을 기반으로 지도를 생성하고, 시간·교통비·체력 등의 제약 조건을 고려하여 경로를 선택하는 방식으로 구현되어 있습니다.

향후에는 기존 게임 구조를 유지하면서 실제 지도 및 교통 데이터를 반영하고, LLM을 활용한 피드백 기능을 추가할 예정입니다.

### 1. 실제 지도 및 이동시간 데이터 반영

- **카카오맵 API**를 활용하여 실제 지하철역의 위치와 노선 연결 관계를 지도에 반영합니다.
- 각 레벨마다 실제 노선의 특정 범위를 선정하여 게임 지도를 구성합니다.
- 공공데이터 또는 대중교통 API를 통해 실제 역간 소요시간을 수집하고, 이를 그래프 간선의 가중치로 활용합니다.
- 실시간 교통 상황을 그대로 재현하기보다는 기준 이동시간을 활용하여 게임의 일관성을 유지합니다.

### 2. LLM 기반 게임 결과 분석

- 게임 종료 후 플레이어의 이동 경로와 서버가 계산한 기준 경로를 비교합니다.
- 이동시간, 교통비, 체력 소모 및 발생한 사건 등을 바탕으로 플레이어의 선택을 분석합니다.
- LLM을 활용하여 경로 선택의 장단점과 다음 플레이에서 개선할 수 있는 부분을 자연어로 제공합니다.
- 게임의 성공·실패 판정과 효율 계산은 기존 게임 엔진에서 처리하며, LLM은 결과 분석 및 피드백 생성에 활용합니다.

### 3. 게임 난이도 및 제약 조건 개선

- 교통수단 이용 제한, 대기시간, 체력 회복 지점 등 다양한 변수를 추가하는 방안을 검토합니다.
- 레벨별로 이동 가능한 구간과 제약 조건을 다르게 설정하여 난이도를 조절합니다.
- 플레이어가 시간·교통비·체력 사이에서 다양한 전략을 선택할 수 있도록 게임 규칙을 개선합니다.
